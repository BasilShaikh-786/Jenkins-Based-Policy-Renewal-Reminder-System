## 1. Overview

The initial version of the application uses a single database table: `POLICY`. This table stores all insurance policy records. Because the application is a monolith and the domain is simple (one policy type), a single table is sufficient and avoids unnecessary complexity.

**Database technology:** H2 in-memory database (development). The JPA entity definition is database-agnostic and can be switched to MySQL or PostgreSQL later by changing only the data source configuration.

### 2.3 Explanation of Key Design Decisions

#### Why is `renewalStatus` only stored as `RENEWED` or null?

This is the most important design decision in the data model. There are two approaches:

**Option A — Store all statuses** (Active, Expiring Soon, Expired, Renewed)  
- Simple to query.  
- Problem: The stored status becomes stale. A policy stored as "Active" today becomes "Expiring Soon" in 25 days, then "Expired" after 30 days — but the stored value still says "Active". This would require a background job to update statuses continuously, which adds complexity.

**Option B — Store only `RENEWED`; derive everything else from dates** (chosen approach)  
- Dates are facts that do not change.  
- Status is always computed fresh from the current date when the page loads.  
- No background update job is needed.  
- The only thing that cannot be derived from a date is whether a human agent has explicitly renewed the policy — so that decision alone is stored.

**Chosen approach: Option B.** This is simpler, more correct and prevents the stale-status problem.

#### Why use `BigDecimal` for premium?

Java `double` and `float` types cannot represent all decimal fractions exactly. For example, `0.1 + 0.2` in floating point gives `0.30000000000000004`. For financial amounts, this is unacceptable. `BigDecimal` stores the exact value as intended.

#### Why store `createdAt` and `updatedAt`?

These fields provide an audit trail. Knowing when a record was created and last modified helps administrators identify stale or forgotten records and supports future audit logging features.

## 4. Status Derivation Algorithm

The following logic is executed in `PolicyService.getDerivedStatus(Policy policy)`:

```
if (policy.getRenewalStatus() != null && policy.getRenewalStatus().equals("RENEWED"))
    return "RENEWED"
else if (policy.getExpiryDate().isBefore(LocalDate.now()))
    return "EXPIRED"
else if (policy.getExpiryDate().isBefore(LocalDate.now().plusDays(alertWindowDays)))
    return "EXPIRING_SOON"
else
    return "ACTIVE"
```

Where `alertWindowDays` is read from `application.properties` (default: 30).

This method is called once per policy when building the list or dashboard. It is never called in templates or repositories.
